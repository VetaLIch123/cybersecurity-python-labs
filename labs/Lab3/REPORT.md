# Звіт до лабораторної роботи №3

## Тема і мета

**Тема:** прикладні бібліотеки Python для побудови вебзастосунків. Реалізовано REST API на FastAPI, моделі Pydantic 2 та SQLite сховище з параметризованими запитами й транзакціями.

## Предметна область — варіант 4

Сервіс зберігає навчальні підсумки спостережень за автентифікацією. Категорія визначає тип події (`failed_login`, `blocked_account`, `mfa_failure`), `value` — цілу невід’ємну кількість подій за інтервал, `status` — стан перевірки (`new`, `in_progress`, `done`). Поріг для аналізу навчальних результатів — 20 подій. Наведені набори синтетичні.

## Структура та запуск

Код розміщений у `labs/Lab3`: `main.py` створює застосунок і підключає маршрути; `database.py` ініціалізує SQLite; `schema.sql` задає дві таблиці; `repository.py` містить параметризовані запити; `schemas.py` перевіряє вхідні дані; `seed.py` перевіряє JSON і заповнює нову базу; `routers/` містить маршрути категорій і записів; `data/seed.json` — відтворювані початкові дані.

Із кореня репозиторію:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
python -m labs.Lab3.database
python -m labs.Lab3.seed
uvicorn labs.Lab3.main:app --reload --host 127.0.0.1 --port 8000
```

Документація API доступна в `/docs`, схема OpenAPI — `/openapi.json`. Ім’я, група та номер варіанта завантажуються з `shared/student.py`.

## Схема бази

- `categories`: додатний первинний ключ `id`; унікальна непорожня назва довжиною 2–40 символів.
- `records`: додатний первинний ключ `id`; унікальний `code` довжиною 3–40; `title` довжиною 3–120; додатний зовнішній ключ `category_id`; `value` має SQLite-тип INTEGER і не може бути від’ємним; `status` обмежений дозволеним набором.
- Зовнішній ключ посилається на `categories(id)` і має `ON DELETE RESTRICT`; для кожного з’єднання ввімкнено `PRAGMA foreign_keys = ON`.

`schema.sql` зберігає готовий варіантний SQL. SQLite-файл створюється локально і виключений із Git; схема та JSON лишаються відтворюваними.

## Початкові дані

Три категорії мають id 1–3. Вісім записів мають коди `V04-01`–`V04-08`, назву «Інтервал автентифікації» з номером, значення `[25, 8, 3, 40, 12, 5, 18, 22]` і статуси згідно з таблицею завдання. Записам відповідають категорії 1, 2, 3, 1, 2, 3, 1, 2. У `seed.py` схема й дані перевіряються до вставлення; категорії з ідентифікаторами та вісім записів додаються в одній транзакції. Повторний запуск на непорожній базі завершується без змін.

## API та безпека даних

Реалізовані `/ping`, `/student`, CRUD для категорій і записів, фільтри списку (`category_id`, `status`, `min_value`, буквальний `q`, `limit`, `offset`) та `POST /records/bulk`. Відповіді запису включають `category_name`. Повна заміна через PUT вимагає всі змінювані поля; поле `id` не приймається у тілі.

Pydantic відхиляє невідомі поля, порожній після обрізання текст, некоректний статус, від’ємне чи дробове `value`, недопустимі ідентифікатори й помилкові параметри сторінки. SQLite `CHECK`, унікальні обмеження і зовнішній ключ додатково гарантують цілісність. Користувацькі значення передаються в SQL окремими параметрами; фільтр пошуку використовує `instr`, тож `%` і `_` є звичайними символами. Технічні деталі SQLite не повертаються клієнту.

Пакет спершу проходить перевірку Pydantic. Вставки виконуються через одне з’єднання в одному транзакційному контексті; помилка унікальності дає 409, відсутня категорія — 404, а всі зміни пакета відкочуються.

## Результати перевірки

Перевірки виконані на локальному FastAPI-сервері та навчальній базі:

| Сценарій | Фактичний результат |
| --- | --- |
| Ініціалізація та два запуски seed | Створено 3 категорії й 8 записів; повторне заповнення повідомило про відсутність змін |
| `/ping`, `/student`, `/categories` | Усі повернули 200; студент — Родич Віталій Андрійович, КБ-205, варіант 4 |
| Фільтр `category_id=1&status=new&min_value=20` | 200; знайдені записи `V04-01` і `V04-04` |
| Створення, читання, PUT, видалення запису | 201, 200, 200, 204; тестовий запис прибрано |
| Дробове `value=1.5` | 422, запис не створено |
| Посилання на категорію 999 | 404 |
| Дублікат коду | 409 |
| Пакет із новим першим записом і дублем другим | 409; пошук першого запису повернув порожній список, транзакцію скасовано |
| Коректний пакет із двох записів | 201; обидва записи створено й після перевірки видалено |
| Пакет з категорією 999 у другому елементі | 404; перший елемент відсутній після запиту |
| Створення та видалення порожньої категорії | 201 і 204 |
| Ruff для `labs/Lab3` | `ruff check labs/Lab3` — без зауважень; `ruff format --check labs/Lab3` — 10 файлів уже відформатовано |

Повна перевірка Ruff для всього репозиторію також виявила наявні проблеми в `labs/lab2/main.py` та відмінності форматування в `labs/lab2/Task1.py` і `Task2.py`. Ці файли вже мали локальні незбережені зміни до початку роботи; вони не змінювалися в межах цієї лабораторної.

## Висновок

Створено відтворюваний API варіанта 4 для підсумків подій автентифікації. Перевірки моделей і обмеження SQLite відхиляють некоректні дані, параметризовані SQL-запити захищають значення фільтрів, а транзакція забезпечує атомарне пакетне додавання.
